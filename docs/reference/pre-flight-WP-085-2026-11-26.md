## Engineering calls (Claude's, with reasoning)

**1. Download, verify and extract in Java, not a port of `backends/dlc/`.**

- *Java route:* the JDK and Android SDK already provide `HttpsURLConnection`,
  `MessageDigest` (SHA-256), `ZipInputStream` and `org.json`. ScummVM's own
  add/detection is reached without new C++: the activity can restart the
  ScummVM thread with new args (`ScummVMActivity.java:1341-1348`,
  `onNewIntent`), and `--add --path=<dir> --recursive --no-exit` runs
  `addGames()` and stays in the launcher (`base/commandLine.cpp:2056,2194-2197`;
  `exit` is a boolean option at `:998`). Estimate: about 500–800 lines of new
  Java, and no C++ beyond an optional JNI hook if the restart route proves
  awkward.
- *DLC port:* `backends/dlc/` is 516 lines plus `gui/dlcsdialog.*` (160). It
  would also need the Android backend to create a store and report
  `kFeatureDLC` (the SDL pattern at `sdl.cpp:108,233`); `configure` enabling DLC
  for Android (`configure:6408`, which needs `_http`); a SHA-256
  implementation, because `common/` has none (a grep for sha256 finds nothing);
  a manifest adapter, because `scummvmcloud.cpp:57` expects Firebase
  `ScummVMCloud` objects; and update and rollback logic, which it lacks
  entirely. That's larger, it's C++ across more files, and it's no better.
- **Call: Java.** It matches WP-085 §Scope 10's preference.

**2. D4, keeping the advanced mode out of the Play build: build-type source
sets.**

- The advanced-mode classes go in their own Java source directory
  (`backends/platform/android/advanced/`), added only to the **debug** build
  type's source set. The release build type gets a same-named stub
  (`backends/platform/android/advanced-stub/`) that reports "not available", so
  `main` code compiles in both. The release build, which is the Play build,
  then contains no advanced-mode class at all, whatever R8 does.
- Why not the alternatives: a product flavor doubles the variants and moves the
  APK output paths that `android.mk:76-99` hard-codes. A `BuildConfig` flag or
  a compile-time define leaves the code in the binary and relies on dead-code
  stripping. The test build is therefore the debug build (id
  `<injected id>.debug`), which is what WP-085's sideload testing installs
  anyway.
- **How EC-008 Step 3 checks it:** on the release APK (or the AAB's base APK),
  `apkanalyzer dex packages --defined-only <apk>` lists no
  `org.scummvm.scummvm.advanced` package (`proguard-rules.pro` is
  `-dontobfuscate`, so the class names survive R8). And `unzip -p <apk>
  'classes*.dex' | strings | grep -c <manifest-URL sentinel>` returns 0. Both
  outputs are captured.

**3. Where extracted packages live: `getFilesDir()/packages/<id>/<version>/`,
with downloads staged in `getFilesDir()/packages/.staging/`.**

- `updateStartSettings` prunes only game domains whose path is under
  `<assets>/games` and no longer exists (`android.cpp:477-509`).
- On an app update, `updateAssetsToInternalMemory()` deletes the data dir's
  top-level *files* but skips folders (`ScummVMActivity.java:2400-2403`,
  `internalAppFolderCleanup`), and fully resyncs only `assets/` and `doc/`
  (`:2581-2582`, `assetsFolderCleanup` at `:2422-2451`).
- The data dir is `getFilesDir()` (`:1899`). A `packages/` folder there
  therefore survives updates and is removed on uninstall, as saves are.
- Staging inside the same folder keeps the verified swap a same-filesystem
  rename, and the cache dir isn't used because Android may clear it mid-download.
- An update unpacks the new version beside the old one and switches the game's
  `path` only after it verifies, which is Milestone 4's rollback guarantee.

## After execution: lessons learned

Filled in 2026-11-27, after execution
([WP-085 §Result](../work-packets/WP-085-tv-app-pipeline.md#result)).

1. **Find out which `adb` reached the TV.** This pre-flight recorded `adb`
   1.0.41 (37.0.3) without saying whose: it was Windows `adb` (winget
   platform-tools), not WSL's. WSL runs in NAT mode, where `adb mdns
   services` finds nothing, which cost a round trip at execution. Builds run
   in WSL; the TV is driven from Windows.
2. **Check the build's optional libraries against the UI it targets.** The
   pre-flight checked Oboe, but not PNG. ScummVM's grid launcher aborts
   without libpng ("No PNG support compiled"). It crashed the app on the TV,
   and the WP-079 app too once its grid view was turned on. A
   `grep USE_PNG config.h` would have caught it.
3. **Probe the platform before planning import routes.** `cmd package
   query-activities -a android.intent.action.OPEN_DOCUMENT_TREE` shows in one
   command that this Google TV has no system picker: only
   `com.android.tv.frameworkpackagestubs` handles it. Run as the app, `ls` on
   the USB stick shows Android 14 blocks reading it by path. Both are
   pre-flight checks. They'd have shown that exit criterion 3 depends on the
   cloud route alone.
4. **Test input on the real remote early.** The TCL remote reports every
   press twice, and its ring sends OK when pressed near the edge. A D-pad
   gesture designed on paper failed by hand. Record `getevent -lt` from each
   input device at Step 1.
5. **Two apps that look alike on one TV get confused.** The WP-079 debug
   app (ScummVM) sat next to the test app, and live checks twice ran in the
   wrong one. Hide the other app for the run (`pm disable-user`, data kept),
   or give the test app art that's clearly different from the start.
6. **Confirm what the peripherals are before Step 1.** "Keyboard, mouse,
   gamepad" turned out to be one keyboard-with-touchpad, with no gamepad. A
   `dumpsys input` with Jeff at the TV, before building, would have shown it.
