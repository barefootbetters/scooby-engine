## After execution — lessons learned

**Lesson: names in the data can stand in for a script.** The clickable sections in `object.ini` are empty. The behaviour comes from the placed ANIM's name: its last letter is the state, and the sound is `SFX_` plus the name. The trace found the rule, and the data check confirmed it on 59 of 96 Showdown clickables before any engine code was written.

**Lesson: use the original's lookup in the reference too.** The reference first looked sounds up in `Sfx.dat` alone. Two clickable sounds live in `Music.dat`, and the first comparison showed six differing lines. The engine was right, because it searches all three files as `0x434DC0` does.

**Lesson: a real mouse needs the window on top.** `SetCursorPos` and `mouse_event` reach SDL only if the ScummVM window is the one under the cursor. A background `Start-Process` doesn't put it there. An Alt key tap, `SetWindowPos(HWND_TOPMOST)` and `SetForegroundWindow` did.

**Lesson: start WP work in its own fork worktree when another session holds the fork checkout.** WP-020 was still editing `C:\dev\scummvm` while this WP was traced. A `git worktree` on WP-020's pushed commit gave this WP a clean base without touching that checkout, and a separate scratch Ghidra project left the shared `scooby.gpr` unlocked.

**Lesson: a reference that shares the engine's reading shares its mistakes.** Both played sequence 0 for an unknown ANIM name, and they matched. The WP-001 session, reading `0x430A00`, `0x4309C0` and `0x430D10`, found that the original shows nothing. WP-018's lesson again: an exact match checks the code against the model, not the model against the binary.

**Scope note:** the lock held. One fork commit, staged by name, fast-forwarded onto `scooby-engine`. The test configuration and the scratch Ghidra projects stayed in the session scratchpad.
