## After execution — lessons learned

- **The two traces agreed with no correction this packet.** Both reads — mine and
  the independent second, handed raw addresses — matched on every slot, clip, flag
  and gate. The dual trace earned its keep anyway on the one non-obvious fact: the
  echo flag.
- **The echo flag (`room+0x29`) was anchored on its reader, not the flag list.**
  The second trace's instruction-scan found its only reader (the wrong-item line
  selector `0x4098B0`): in an echo room the characters' `_Echo_` lines play and
  Fred, who has none, is passed over. The fork already carried a comment
  anticipating this ("no room of the default class sets it"), so the room is the
  first to need it; wired as `RoomHooks::isEcho` with one reader in `inventory.cpp`
  — a sibling hook staged by name, no change for any other room. This is the
  WP-076 flag-naming discipline applied: never infer a flag's meaning from its
  offset; decompile its reader.
- **The `0x408C80` vs `0x408DC0` builders map to different claim kinds.** The
  spell book is built by `0x408C80` → a **requires** object (the arrow answers);
  the hotspot by `0x408DC0` → a **clickable**. Reading the builder address, not
  guessing from the object's role, kept the claim kinds right.
- **One interpretive call, flagged:** the spell-book `event` guards on the cursor
  being the settled default (`0x433300` of the cached cursor against the live
  one); ported as a plain-click guard (`Inventory::isDefaultCursor`), which is the
  condition under which the requires object's event fires anyway.
- The Ghidra "warm project holds Showdown" hazard (WP-076) held again: Phantom was
  imported into a throwaway scratchpad, read-only; the committed project was left
  untouched.
- **Headless-run note (tooling, not the WP):** the graceful `taskkill //IM
  scummvm.exe //T` the run-check recipe uses was blocked by the sandbox classifier
  this session. ScummVM routes `debugC` through `logMessage`, which `fflush`es to
  stdout per line, so the check output is captured live without a close; the run
  is launched as a background task's main process (via `exec`) and torn down with
  the harness's task-stop. Worth adding to the run-check recipe as the fallback
  when `taskkill` is unavailable.
