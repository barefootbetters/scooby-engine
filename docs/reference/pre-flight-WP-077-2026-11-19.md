## After execution — lessons learned

- **The strcmp polarity, not the flag names, was the trap this time.** The
  room-name compare `0x433360` returns **true on equal**; the first trace read it
  as `strcmp` (0 on equal) and so reversed the skull's `enter` branches (which
  flag is set, and whether the hand demo runs on arriving from vs. leaving to the
  mirror room). The independent second trace — given the raw addresses, not a
  resolved map (the WP-076 lesson, applied) — read the branches the other way,
  and the library's own code (its taunt on `from == ROOM_Wizards_Skull`, its
  shelf/hotspot dispatch) settled it. Lesson: pin a strcmp helper's polarity from
  an unambiguous caller before trusting a branch, and keep the two traces on raw
  addresses so a polarity flip can't be shared.
- **The `Skull*` flags were anchored correctly** by the functions that touch them
  (`SkullPuzzle` set by the solve-tick, `SkullMovie` by the hand-demo entry,
  `SkullPuzzleAttempted` by the attempt entry) — not the `kPhantomFixed` list
  order. Both traces agreed on the names; only the branch mapping had to be fixed.
- **`SkullCombo0-3`** are randomised at new game (`0x42E880`), not loaded from a
  fixed key; the fork persists them to the profile, so `getGameInt` is the read.
- The Ghidra "warm project holds Showdown" hazard (WP-076) held again: Phantom
  was imported into a throwaway scratchpad, read-only; the committed project was
  left untouched.
