## After execution — lessons learned

**Lesson: a setter's caller tells you what it does.** `0x434F10` and `0x434F30` only store a flag, a number and a count. What they mean came from the one function that reads those fields every tick (`0x434C00`), found by asking which code calls it and how often.

**Lesson: C++ evaluates arguments in any order.** A check line called `changes(10)` and `isMusicFading()` in one `debugC`; the engine printed the fading flag from before the ticks and disagreed with the reference. Compute side effects before the log line.

**Lesson: a hook point carries an order.** The room load's fade-up comes after the room's entry, so a scene started during the entry has its dip cancelled at once. Hooked before the entry, the fork would have kept a dip the original never has. Reading where the call sits in the original, not just that it exists, settled where the fork's goes.

**Scope note:** the lock held: one fork commit staged by name. The other session's files got the hook calls it named, and the credits' row in its setup table, which it was told about; its setup check's one credits line changes accordingly.
